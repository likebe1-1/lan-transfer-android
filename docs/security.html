v2.3.0 安全基线

局域网传输，
也要能证明“对面是谁”。

LanLink 不上传云端、不收集数据；同时用证书/主机密钥固定、服务端限流、系统级凭据加密与签名更新，把“同网段就能伪造”的常见风险挡在外面。下面是全部安全机制与已知取舍。

传输认证

不只是“加密”，还要防冒充

自签证书只加密不认证时，同网段中间人可以完整解密。LanLink 让发送方把身份指纹随二维码/广播下发，接收方只信任该指纹。

FTPS 证书固定

发送方把自签名证书的 SHA-256 指纹写入二维码/局域网广播；接收方只接受该指纹的证书，指纹不符直接握手失败。

SFTP / SCP 主机密钥固定

同理固定 SSH 主机密钥指纹（OpenSSH 线格式 blob 的 SHA-256），中间人无法出示同指纹主机密钥。

加密协议优先

自动连接顺序为 FTPS → SFTP → SCP；明文 FTP 不再自动尝试，只能由用户手动指定。

旧版兼容且不降级

对端是旧版本、没有指纹时退回首次信任，但界面会明确提示“本次未校验证书/主机密钥”。

认证与防爆破

接收码很短，防线在服务端

6~8 位数字的熵有限，仅靠客户端限流可以被任意 FTP/SSH 客户端绕过；LanLink 在三层做服务端限流。

8 位接收码

空间从 90 万提升到 1 亿（兼容旧版 6 位）；接收码只通过对方屏幕或二维码传递，UDP 广播不携带。

单来源逐级锁定

同一 IP 10 分钟内失败 5 次即锁定；可信来源（近期成功认证过）按 1/5/10 分钟阶梯升级，减少 NAT 后邻居误伤。

全局失败速率上限

全服务 60 次失败/分钟触发 30 秒全局冷却，阻断“换 IP 水平爆破”；冷却期快速失败，不产生状态膨胀。

四协议统一生效

FTP、FTPS、SFTP、SCP 共用同一限流器；SSH 密码认证与 FTP USER/PASS 阶段都会拦截。

本地数据

手机上的密码不再明文

Keystore AES-256-GCM

服务器密码与传输队列里的凭据使用 Android Keystore 密钥加密落盘（enc:v1: 前缀，随机 IV），密钥不可导出。

不参与云备份

allowBackup=false，凭据不会被系统备份带到其他设备；解密失败时要求重新输入而不是崩溃。

密钥与令牌不入库

签名 keystore、更新签名私钥、Gitee/GitHub 令牌全部放在项目外并通过环境变量注入，仓库内无明文凭据。

更新链

镜像站也改不了更新内容

更新清单必须带 Ed25519 签名；下载的 APK 再校验大小、SHA-256、签名证书与版本号，任何一步不符都取消安装。

仅 HTTPS + 签名清单

非 HTTPS 来源直接跳过；清单签名无效或缺失即拒绝，签名公钥内置在 App 内。

APK 多层校验

下载后校验 size / SHA-256 / APK 签名证书 / versionCode，全部一致才拉起系统安装器。

调试版隔离

debug 包与 release 包证书不同，调试版直接禁用应用内更新并提示安装正式版，避免“下载完才发现签名不匹配”。

已知取舍

透明说明边界，而不是“绝对安全”

场景现状与原因
局域网可见性发现依赖 UDP 广播（明文，但不含接收码）；同一 Wi-Fi 内的设备可以看到设备名/IP/端口。这是“附近设备”功能的前提。
服务端监听 0.0.0.0为支持热点/多网卡场景绑定全部网卡；已由服务端限流与加密协议降低风险，后续可加“仅私有网段来源”开关。
普通客户端首次信任手动连接任意 FTPS/SFTP 服务器时，默认严格校验证书；用户显式勾选“信任任意证书”才会放宽。快速传文件走指纹固定。
明文 FTP仍保留（兼容老设备），但自动回退不选它；需要用户手动指定，并自行承担明文风险。
SCP 能力边界SCP 不支持断点续传与结构化列目录；应用优先 SFTP，失败才回退 SCP。

签名私钥更新签名私钥离线保管、不入库；丢失后无法再为已发布 App 签发可验证的新清单。
